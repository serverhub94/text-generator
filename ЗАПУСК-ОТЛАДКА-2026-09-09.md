## 3. Пред-существующие баги ветки

Все они появились в коммитах про выбор модели (`74ed83c`, `c3333e7`, `dafcc9a`) и на момент

### 3.1. `config/textgen.php:21` — `default_model` не совпадает с ключами реестра моделей

```php
// config/textgen.php
20: 'model'         => env('TEXTGEN_MODEL', 'claude-opus-5'),   // ← ID для API, ОК
21: 'default_model' => env('TEXTGEN_MODEL', 'claude-opus-5'),   // ← ключ профиля, НЕВЕРНО
...
186: 'models' => [

      'sonnet-5'  => [ ... ],
      'haiku-4-5' => [ ... ],
```

`ModelProfile::fromConfig()` (`app/Services/ModelProfile.php:17-23`) ищет ключ в
`config['models'][$key]` и бросает исключение, если не нашёл:

```php
// app/Services/ModelProfile.php:19-20
if (!isset($config['models'][$key])) {
    throw new InvalidArgumentException("Unknown model: {$key}");
}
```

**Последствие:** `Pipeline::run()` (`app/Services/Pipeline.php:104-133`) при отсутствии
`$input['model']` откатывается на `config['default_model']` = `claude-opus-5`, которого
в реестре нет → `InvalidArgumentException: Unknown model: claude-opus-5`.

Это ровно те **16 ошибок в `tests/Unit/PipelineTest.php`** (строки 42, 56, 68, 84, 94, 103,
111, 121, 144, 156, 167, 182, 194, 206, 235).

**Почему веб-форма всё равно работает:** в `generator/index.blade.php:137-145` селектор
перебирает `config('textgen.models')` и присылает валидный ключ (`opus-5`), контроллер
`GeneratorController::store()` (строки 115-159) сохраняет его в `runs.model`, а
`RunPipeline::handle()` (строки 88-93) кладёт его в `$input['model']`. Ветка «нет модели»
в реальном сценарии не срабатывает.

**Как чинить (одно из):**
- в `.env` поставить `TEXTGEN_MODEL=claude-opus-5` для API (как есть) **и** добавить
  отдельный `TEXTGEN_DEFAULT_MODEL=opus-5`, а `config/textgen.php:21` читать из него;
- либо переименовать ключи в `config/textgen.php` `models` в `claude-opus-5` / `claude-sonnet-5` / `claude-haiku-4-5`;
- либо в реестре моделей выставлять `id` = реальный API-идентификатор и брать `model` для API из профиля.

### 3.2. `app/Models/Run.php:37-55` — колонка `stage` (ед. ч.) отсутствует в `$fillable`

Миграция `database/migrations/2026_09_01_011717_create_runs_table.php:23` создаёт колонку:
```php
$table->string('stage')->nullable();
```
но в `$fillable` перечислена только `stages` (мн. ч., строка 45) — `stage` пропущена.

**Последствие:** `Run::create(['stage' => ...])` и `$run->update(['stage' => ...])`
молча отбрасывают значение (mass-assignment). Это **2 падения в `tests/Feature/GeneratorTest.php`**:
- `test_the_status_endpoint_reports_progress` (строка 115) — ждёт `stage => 'research'`, получает `null`;
- `test_a_rewrite_stage_reports_its_attempt_number` (строка 134) — ждёт `stage_label`, получает `null`.

**Почему живой прогресс в UI всё равно работает:** `RunPipeline::handle()` пишет стадию
через `forceFill`, а не `update` (`app/Jobs/RunPipeline.php:64-66`):
```php

```
`forceFill` игнорирует `$fillable`, поэтому опрос `/run/{run}/status` в реальном прогоне
отдаёт стадию корректно.

**Как чинить:** добавить `'stage',` в массив `$fillable` в `app/Models/Run.php`.

### 3.5. `tests/Feature/AccessCodeTest.php` — тесты не обновили под новый роут `/access`

Тесты постят код доступа на `route('runs.create')`, т.е. на `POST /`:

Но флоу ввода кода переехал на отдельный роут `POST /access` (`routes/web.php:9-49`,

### 3.6. 🔴 КРИТИЧНО — `app/Services/ModelProfile.php:75-78` — `thinking()` объявлен `: string`, а в конфиге это массив

**Это блокирует ЛЮБОЙ реальный прогон генерации, а не только тесты.**

```php
// app/Services/ModelProfile.php:75-78
public function thinking(): string
{
    return $this->cfg['thinking'] ?? 'none';
}
```

Но в `config/textgen.php` (строки 200, 218, 236) `thinking` у каждой модели — это **список
допустимых значений**, а не одно текущее:

```php
'opus-5' => [
    ...
    'effort'   => ['low', 'medium', 'high'],
    'thinking' => ['none', 'short', 'long'],   // ← массив
    ...
],
```

**Симптом (мой тестовый прогon V1, прогон `01a086ec-…`, задача упала за 148 мс):**
```
App\Services\ModelProfile::thinking(): Return value must be of type string, array returned
```
Стек: `RunPipeline::handle()` → `Pipeline::run()` → `Pipeline::stageCall()` →
`ClaudeService::send()` → `$profile->thinking()` (`app/Services/ClaudeService.php:95`).

**Первопричина:** коммит `74ed83c` в `ClaudeService::send()` заменил рабочий код

```php
// было (коммит 376f227, работало):
outputConfig: ['effort' => $effort],
thinking:     ['type' => 'adaptive'],
```

на логику от профиля (`app/Services/ClaudeService.php:90-137`), которая:
1. зовёт `$profile->thinking()` — падает по типу (см. выше);
2. даже если починить тип — строит `thinking: ['type' => 'short'|'long'|'none']`,
   где `'short'/'long'` — не валидные значения `thinking.type` для Anthropic SDK
   (ожидается `adaptive` / `enabled` / `disabled`), т.е. следующий шаг — 400 от API;
3. добавляет в `outputConfig` ключ `maxOutputTokens` (`ClaudeService.php:114`),
   которого в исходном рабочем вызове не было — тоже кандидат на 400.

**Аналогично рискованно** `ModelProfile::webTools()` (строка 80-83) — возвращает
`$this->cfg['web_tools']` (в конфиге это строка `'full'|'limited'|'none'`, тут ОК),
но `effort` в конфиге — массив, а профиль ждёт список (`effortFor()`, строка 48-67) —
это единственное место, где семантика «список допустимых» выдержана.

**Как чинить (минимально, чтобы прогоны заработали):**
вернуть в `ClaudeService::send()` для случая, когда профиль не даёт валидного
скалярного значения, исходное поведение:
```php
outputConfig: ['effort' => $effort],
thinking:     ['type' => 'adaptive'],
```
Полноценный фикс — договориться о структуре: в конфиге хранить и «список допустимых»,
и «значение по умолчанию» отдельно, а `ModelProfile::thinking()`/`effort()` вернуть
одно валидное значение из белого списка Anthropic.

**Статус:** применён минимальный фикс — см. §2.2. `ModelProfile::thinking()` в коде
остался как есть (объявление `: string` при массиве в конфиге), просто его больше
никто не вызывает.
